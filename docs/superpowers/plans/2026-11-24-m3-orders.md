# M3 주문·트랜잭션 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**

- 주문 목록·상세와 상태 전이(확정·출고·완료·취소)를 API와 어드민 화면 양쪽에서 완성한다.
- 핵심은 **주문 확정 트랜잭션**이다. 재고를 비관적 락으로 차감하며, 동시성·원자성·교착 방지를 실제 DB 테스트로 증명한다.
- 상품 화면에 재고 수동 조정과 재고 이력을 추가한다.

**Architecture:**

- **`inventory/` 모듈 신설**
  - 재고 변경의 단일 창구(`InventoryLedger`)와 이력(`InventoryHistory`)을 둔다.
  - 도메인 파일을 import하지 않도록 `inventories` 테이블은 `manager.query` SQL로 다룬다. 의존 방향은 `orders → inventory ← products`이고, 순환은 없다.
- **`orders/` 모듈**
  - `Order`·`OrderItem`·`OrderStatusHistory`·`order_sequences`와 상태 머신(계약 패키지의 순수 함수)을 둔다.
  - 상태 전이는 모두 한 트랜잭션에서 처리한다. 잠금 순서는 주문 행 → 재고 행(productId 오름차순)이다.
- **Web**
  - 주문 목록: `entities/order`, `widgets/order-table`, `features/order-filter`, `views/order-list`
  - 주문 상세: `features/change-order-status`, `widgets/order-timeline`, `views/order-detail`
  - 상품 화면 확장: `features/adjust-inventory`, `widgets/inventory-history`

**Tech Stack:** 기존 스택 그대로다(NestJS 12, TypeORM 1.x, PostgreSQL 16, Next.js 16, TanStack Query/Table, Zustand, RHF + zod, Vitest, Testcontainers, MSW). 새 라이브러리는 없다.

## Global Constraints

- 공통 규칙은 `CLAUDE.md`를 따른다. 이 섹션은 M3 고유 값만 적는다.
- **주문 상태와 라벨:** `PENDING`(접수)·`CONFIRMED`(확정)·`SHIPPED`(출고)·`DELIVERED`(배송완료)·`CANCELLED`(취소)
- **허용 전이:**
  - `PENDING→CONFIRMED`(confirm)
  - `CONFIRMED→SHIPPED`(ship)
  - `SHIPPED→DELIVERED`(deliver)
  - `PENDING→CANCELLED`, `CONFIRMED→CANCELLED`(cancel)
  - 그 밖은 409 `CONFLICT`, `details: { from, to }`
- **재고 증감:**
  - 확정은 품목 수량만큼 차감, 확정 주문의 취소는 원복한다.
  - `PENDING` 취소·출고·완료는 재고를 바꾸지 않는다.
  - 재고는 확정 시점에만 잡는다(예약 없음).
- **잠금 순서**(모든 재고 변경 경로 공통)
  1. 주문 행(`FOR UPDATE`)
  2. 재고 행: `WHERE "productId" = ANY($1) ORDER BY "productId" FOR UPDATE`
  - 트랜잭션 안의 조회와 쓰기는 모두 그 트랜잭션의 `manager`로 한다.
- **재고 부족:**
  - 하나라도 부족하면 전체 롤백한다.
  - 응답은 422 `INSUFFICIENT_STOCK`이고, `details: InsufficientStockItem[]`(`{ productId, sku, name, requested, available }`)에는 부족한 품목만 담는다.
- **주문번호:**
  - 형식은 `ORD-{YYYYMMDD}-{NNNN}`이다. 날짜는 KST 기준이고, 일련번호는 그날 1부터 시작해 4자리로 0을 채운다.
  - 발급은 `order_sequences(day date PK, last int)`에 `INSERT … ON CONFLICT (day) DO UPDATE SET last = order_sequences.last + 1 RETURNING last`로 원자적으로 한다.
- **금액:** `OrderItem.unitPrice`는 주문 시점 가격의 스냅샷이다. `totalAmount = Σ unitPrice × quantity`(정수 원)이다.
  - `OrderItem`에는 `productName`·`sku` 스냅샷도 저장한다. 상품이 바뀌거나 삭제돼도 주문 화면이 유지되게 하기 위해서다.
- **재고 수동 조정:** `PATCH /products/:id/inventory`, body `{ delta, note }`
  - `delta`: 0이 아닌 정수, `-1_000_000..1_000_000`
  - `note`: 1–200자, trim
  - 결과 재고가 음수면 422 `INSUFFICIENT_STOCK`이다.
  - 이력 reason은 `MANUAL_ADJUST`다.
- **재고 이력:** `InventoryHistory`의 필드는 다음과 같다.
  - `id`, `productId`, `delta`, `quantityAfter`
  - `reason`(`ORDER_CONFIRM`·`ORDER_CANCEL`·`MANUAL_ADJUST`)
  - `note` (null 허용)
  - `refOrderId`·`actorId` (null 허용)
  - `createdAt`
- **목록 쿼리:**
  - `GET /orders`
    - `page`·`size`
    - `status`(하나)
    - `from`·`to`: `YYYY-MM-DD`, **KST 날짜 경계**. `from`은 00:00 KST 이상, `to`는 다음 날 00:00 KST 미만이다. `from > to`면 400.
    - `q`(1–50자, `orderNo`·`customerName` ILIKE, 공용 `escapeLike`)
    - `sort`(`createdAt`·`totalAmount` : `asc`·`desc`, 기본 `createdAt:desc`, 동률은 `id ASC`)
  - `GET /products/:id/inventory-history`는 `page`·`size`(기본 10)를 받고 최신순이다.
- **권한:**
  - 조회(`GET /orders`, `GET /orders/:id`, `GET /products/:id/inventory-history`)는 VIEWER 이상이다.
  - 전이·재고 조정·가상 주문 생성은 MANAGER 이상이다.
  - `POST /dev/orders/random`은 `NODE_ENV=production`이면 404다(라우트가 없는 것처럼 동작).
- **시드:**
  - 주문 1,500건을 최근 90일(KST)에 분포시킨다. PRNG 시드는 `20261124`다.
  - 상태 분포는 DELIVERED 55%·SHIPPED 10%·CONFIRMED 10%·PENDING 15%·CANCELLED 10%다.
  - 품목은 1–4개, 수량은 1–3개다.
  - 상태 이력은 전이 경로대로 기록하며, actor는 manager 계정이다.
  - **주문 테이블이 비어 있을 때만** 생성한다(멱등). 시드 주문은 재고와 재고 이력을 건드리지 않는다. 현재 재고를 "그 이후 상태"로 본다. 이 점을 README에 적는다.
- **라벨:** 재고 사유 라벨은 주문 확정·주문 취소·수동 조정이다.

## Review Focus

1. **같은 재고를 두고 동시에 확정**: 재고 10개, 수량 6짜리 주문 두 건을 동시에 확정하면 정확히 하나만 200이고 다른 하나는 422다. 최종 재고는 4, 재고 이력은 1건이다. → Task 6
2. **교착 상태**: 주문 X(상품 A, B)와 주문 Y(상품 B, A)를 동시에 확정해도 40P01 없이 둘 다 성공하거나, 둘 다 정상 응답(200/422)으로 끝난다. → Task 6
3. **부분 부족의 원자성**: A는 충분하고 B만 부족하면, A 재고·주문 상태·이력 모두 그대로다. 422 details에는 B만, `available`과 함께 담긴다. → Task 6
4. **중복 클릭과 오래된 화면**: 확정을 두 번 보내면 두 번째는 409이고 재고는 한 번만 줄어든다. 화면은 409를 받으면 "다른 사용자가 먼저 상태를 바꿨습니다"를 보여 주고 상세를 다시 불러온다. → Task 6, Task 9
5. **KST 날짜 경계**: `to=2026-11-20`은 11-20 23:59 KST 주문을 포함하고 11-21 00:00 KST 주문은 제외한다. UTC로 자르면 9시간이 어긋난다. → Task 5, Task 8
6. **주문번호 동시 발급**: 같은 날 동시에 20건을 생성해도 번호가 겹치지 않는다. → Task 4
