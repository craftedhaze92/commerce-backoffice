**Goal:**

- 설계서 §13의 M6(사용자 관리, Swagger 정리, README, 배포)를 끝낸다.
- M2~M5에서 미뤄 둔 항목을 정리한다: 고아 이미지 정리, 주문 상세의 삭제 상품 표시, 에러 문구 한국어 일원화.
- 저장소가 공개되었고 데모를 공개 배포하므로, 공개 환경에서 깨지거나 악용될 수 있는 지점을 막는다: 데모 계정 보호, 로그인 시도 제한, 프록시 뒤 설정.

**Architecture:**

- **사용자 관리 API (`users/`)**
  - `POST /users`, `PATCH /users/:id`를 추가한다.
  - 자기 자신 변경 금지와 "마지막 활성 ADMIN" 보호는 서버가 트랜잭션 안에서 강제한다. ADMIN 행을 잠가 동시 변경에도 ADMIN이 0명이 되지 않는다.
  - 비활성화하면 같은 트랜잭션에서 그 사용자의 refresh 토큰을 폐기한다. `users/`는 `auth/`를 모르므로 `refresh_tokens` 테이블을 SQL로 갱신한다.
- **고아 이미지 정리 (`products/images/`):** `@nestjs/schedule` 크론으로 하루 한 번 실행한다. DB 행은 트랜잭션으로 지우고, 커밋한 뒤에 오브젝트 스토리지 키를 지운다.
- **공개 배포 대비**
  - `DEMO_MODE`이면 시드 데모 계정 세 개의 역할·활성 상태를 바꿀 수 없다.
  - 로그인은 `@nestjs/throttler`로 "클라이언트 IP + 이메일" 단위로 시도 횟수를 제한한다.
  - `TRUST_PROXY`로 프록시 홉 수를 지정해 `req.ip`와 `Secure` 쿠키가 프록시 뒤에서도 맞게 동작하게 한다.
- **Web**
  - `features/create-user`, `features/manage-user`로 사용자 추가·역할 변경·활성 전환을 만든다.
  - `shared/api`에 에러 코드 → 한국어 문구 매핑을 한 곳에 둔다.
- **문서·배포:** Swagger 태그·응답 정리, README 최종본(스크린샷·구조도), `docs/deploy.md`(Vercel + Railway + Cloudflare R2). **계정 생성과 실제 배포는 사용자가 한다.** 이 계획은 코드·설정·절차서까지만 만든다.

## Global Constraints

- 공통 규칙은 `CLAUDE.md`를 따른다. 이 섹션은 M6 고유 값만 적는다.
- **새 에러 코드(계약 `ErrorCode`):**
  - `DEMO_PROTECTED`(403)
  - `TOO_MANY_REQUESTS`(429)
  - 사용자 관리 충돌은 기존 `CONFLICT`(409)에 `details.reason`을 붙인다: `EMAIL_TAKEN` · `SELF_CHANGE` · `LAST_ADMIN`
- **사용자 생성 `POST /users`(ADMIN)**
  - 입력: `{ email, name, role, password }`
    - `email`은 공용 정규화(trim + 소문자)를 거친다.
    - `name`은 1–50자, trim한다.
    - `password`는 8–72자다(bcrypt 한계).
  - 응답은 201과 `UserListItem`이다. 이미 있는 이메일이면 409 `EMAIL_TAKEN`이다.
- **사용자 수정 `PATCH /users/:id`(ADMIN)**
  - 입력: `{ role?, isActive?, name? }`. 최소 한 필드가 있어야 하고, 없으면 400이다.
  - 응답은 200과 `UserListItem`이다.
  - 자기 자신의 `role`·`isActive` 변경은 409 `SELF_CHANGE`다. 자기 이름 변경은 허용한다.
  - 결과적으로 활성 ADMIN이 0명이 되는 변경(마지막 활성 ADMIN의 강등·비활성화)은 409 `LAST_ADMIN`이다.
  - 판정은 트랜잭션 안에서 활성 ADMIN 행을 `FOR UPDATE`로 잠근 뒤 한다.
  - `isActive: false`가 되면 같은 트랜잭션에서 그 사용자의 미폐기 refresh 토큰에 `revokedAt = now()`를 기록한다.
  - `DEMO_MODE=true`에서 대상이 시드 데모 계정(`admin@demo.com`·`manager@demo.com`·`viewer@demo.com`)이면 `role`·`isActive` 변경은 403 `DEMO_PROTECTED`다. 이름 변경은 허용한다.
- **환경 변수(새로 추가, `.env.example`에도 기록)**
  - `DEMO_MODE`: `true`/`false`, 기본 `false`
  - `TRUST_PROXY`: 0 이상 정수, 기본 `0`. 0이면 설정하지 않고, 0보다 크면 `app.set('trust proxy', n)`한다.
  - `LOGIN_THROTTLE_LIMIT`: 기본 `10`
  - `LOGIN_THROTTLE_TTL_SEC`: 기본 `600`
- **로그인 제한**
  - `POST /auth/login`만 대상이다. 키는 `${req.ip}:${정규화한 email}`이다.
  - TTL 동안 limit을 넘으면 429 `TOO_MANY_REQUESTS`를 돌려주고, `Retry-After` 헤더(초)를 붙인다.
  - 성공한 로그인도 횟수에 포함한다(단순화).
  - e2e는 env로 limit을 낮춰 검증한다.
- **고아 이미지 정리**
  - 매일 04:00 KST(`'0 0 4 * * *'`, `timeZone: 'Asia/Seoul'`)에 실행한다.
  - 정리 대상(설계서 §9-6):
    1. `productId IS NULL`이고 `createdAt < now − 24h`인 이미지. 저장하지 않은 업로드와 PATCH로 떼어낸 이미지가 여기에 해당한다.
    2. `deletedAt < now − 24h`인 소프트 삭제 상품에 붙은 이미지
  - 한 번에 최대 500행, 남으면 반복한다.
  - 행 삭제: 트랜잭션 안에서 `SELECT … FOR UPDATE SKIP LOCKED`로 대상을 잠그고, `DELETE … RETURNING "objectKey","thumbKey"`를 실행한다.
    - 1번 조건은 삭제 시점에 `productId IS NULL`을 다시 확인한다. 그래서 그 사이 연결된 이미지는 지우지 않는다.
  - 스토리지 삭제는 **커밋 후에** `OBJECT_STORAGE.delete(keys)`로 한다. 실패하면 경고 로그만 남긴다(DB가 없는 키를 가리키는 일은 생기지 않고, 고아 오브젝트만 남는다).
  - 현재 시각은 `CLOCK`으로 주입한다.
- **주문 상세의 삭제 상품:** `OrderItemView`에 `productDeleted: boolean`을 추가한다. 화면은 삭제된 상품이면 링크 없이 상품명과 "삭제된 상품" 뱃지를 보인다.
- **에러 문구**
  - API의 `message`는 영어(개발자용)로 둔다.
  - 화면에 보이는 문구는 항상 `shared/api`의 `errorMessage(err, overrides?)`가 에러 코드로 정한 한국어다.
  - 화면 코드에서 `ApiError.message`(서버 문자열)를 사용자에게 직접 보여 주는 곳을 없앤다.
- **Swagger(`/api/docs`)**
  - 모든 컨트롤러에 `@ApiTags`를 단다: `auth`, `users`, `categories`, `products`, `product-images`, `inventory`, `orders`, `dashboard`, `health`.
  - `/dev/*`는 문서에서 뺀다(`@ApiExcludeController`).
  - export 두 개는 `@ApiProduces(xlsx)`와 바이너리 응답으로, `days`는 `enum: [7, 30, 90]`으로 표시한다.
  - 공통 에러 응답 스키마 `ApiErrorBody`를 컴포넌트로 등록한다.
  - production에서도 문서를 연다(공개 데모).
- **데모 계정 문구:** 배포 데모의 비밀번호는 README에 적힌 데모 비밀번호와 같다. 로그인 화면의 데모 계정 빠른 선택은 그대로 둔다.

## Review Focus

1. **마지막 ADMIN 경쟁**: 활성 ADMIN 두 명이 동시에 서로를 강등하면, 한쪽은 200이고 다른 쪽은 409 `LAST_ADMIN`이다. 최종 활성 ADMIN은 1명 이상이다. 잠금이 없으면 둘 다 성공해 0명이 된다. → Task 1
2. **비활성화 즉시 반영**: 비활성화된 사용자는 남은 access 토큰으로 요청해도 401이다. 남은 refresh 토큰으로 갱신해도 실패하고, 그 토큰 행은 `revokedAt`이 기록되어 있다. → Task 1
3. **고아 정리와 동시 연결**: 정리가 대상 행을 고른 뒤 같은 이미지가 상품에 연결되는 경우, 연결이 이기면 이미지는 남고 정리가 이기면 연결은 기존 규칙대로 실패한다(400). 어느 쪽이든 상품이 사라진 키를 가리키지 않는다. → Task 3
4. **프록시 뒤 로그인 제한**: `TRUST_PROXY=1`이면 `X-Forwarded-For`의 클라이언트마다 따로 센다. 0이면 헤더를 믿지 않는다(위조로 우회 불가). 한 사용자의 초과가 다른 이메일·다른 클라이언트를 막지 않는다. → Task 5
5. **데모 보호와 자기 변경**: `DEMO_MODE`에서 ADMIN 데모 계정이 다른 데모 계정을 비활성화하려 하면 403이다. 데모가 아닌 계정은 정상 변경된다. 자기 역할 변경은 DEMO_MODE와 무관하게 409다. 화면은 자기 행의 역할·활성 컨트롤을 비활성화한다. → Task 1, Task 2

**Interfaces:**

- Produces:
  - `errorMessage(err: unknown, overrides?: Partial<Record<ErrorCode | ConflictReason, string>>): string`
    - 기본 문구는 다음과 같다.
      - `VALIDATION_FAILED`: "입력값을 확인해 주세요."
      - `UNAUTHORIZED`: "로그인이 필요합니다."
      - `FORBIDDEN`: "권한이 없습니다."
      - `NOT_FOUND`: "대상을 찾을 수 없습니다."
      - `CONFLICT`: "다른 변경과 충돌했습니다. 새로고침 후 다시 시도해 주세요."
      - `DEMO_PROTECTED`: "데모 계정은 변경할 수 없습니다."
      - `TOO_MANY_REQUESTS`: "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."
      - 그 밖(`INTERNAL`·네트워크 포함): "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해 주세요."
    - `CONFLICT`의 `details.reason`이 있으면 reason 키의 override를 먼저 본다.
    - 기존 화면의 고유 문구(409 상태 전이 안내, 422 재고 부족, 엑셀 한도 등)는 각 feature가 override로 계속 지정한다(**문구 변경 없음**).
  - 사용자 관리 화면 (ADMIN)
    - 머리에 "사용자 추가" 버튼이 있다. 다이얼로그에서 이메일·이름·역할·초기 비밀번호를 입력하며, zod로 검증하고 `USER_LIMITS`를 쓴다.
    - 성공하면 users 쿼리를 invalidate하고 "사용자를 추가했습니다"(role=status)를 보인다.
    - 409 `EMAIL_TAKEN`이면 이메일 필드에 "이미 사용 중인 이메일입니다"를 보인다.
    - 각 행
      - 역할 선택(`ROLE_LABEL`)이 있고, 바꾸면 즉시 PATCH한다.
